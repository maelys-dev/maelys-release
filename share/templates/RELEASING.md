# Releasing @PRODUCT@

Releases go through the shared maelys-release socle, at the version
`.github/workflows/release.yml` pins. The
workflow `.github/workflows/release.yml` and `scripts/checkout-dependency.sh`
are generated by its `maelys-release adopt` from `VERSION`, `dependencies/*.pin`,
`dependencies/packages` and `packaging/homebrew/*.rb.in`.

1. On `main`, up to date with `origin/main`: the dated `CHANGELOG.md` entry
   `## X.Y.Z — YYYY-MM-DD` written, generated documentation regenerated,
   everything else committed. `VERSION` is written by `cut`, whose commit
   carries the bump and nothing else. Before a first release or after a
   packaging change, `maelys-release rehearse . linux-arm64` replays the
   Linux build job in Docker.
2. `maelys-release cut . X.Y.Z --apply` from any maelys-release checkout (it
   runs as the pinned version). It holds the gate first — signing
   configuration, previous tag, free `vX.Y.Z`, `release` environment, the
   same one `maelys-release preflight .` reads without writing anything —
   then commits `VERSION` signed on `release/vX.Y.Z`, opens the pull request
   and waits for its checks (`ci.yml` runs the socle's `check-product.yml`
   on the three release targets).
3. Merge that pull request under this repository's own rules. `cut` never
   merges its own.
4. `maelys-release cut . X.Y.Z --tag --apply`: it verifies the merge commit
   of that pull request is on `main` and carries `VERSION` = `X.Y.Z`, waits
   for every check of that exact commit, then signs `vX.Y.Z` on it — the
   merge commit, never the branch — and pushes it.
5. The workflow verifies the signed annotated tag, clones the pinned
   dependencies, installs the declared packages, builds the packages on
   Linux x86_64, Linux arm64 and macOS arm64, attests their provenance
   (public repository only: a private one ships the signed tag and
   `SHA256SUMS`), publishes the GitHub release, then renders and publishes
   the Homebrew formula with its bottles.
6. Verify: `gh release view vX.Y.Z`, `gh attestation verify ASSET --repo
   OWNER/REPO --signer-repo maelys-dev/maelys-release` (the attestation is
   signed by the socle's reusable workflow), `brew install
   maelys-dev/tap/@PRODUCT@`.

Upgrade the socle with `maelys-release adopt DIR --apply` from a maelys-release
checkout at the wanted tag; `maelys-release check DIR` reports drift with exit 2.

## Replaying the release of a tag

When a release or its tap jobs failed for a reason outside the code — a
cancelled job, an expired approval, a tap push lost to a race — run the
`release` workflow by hand on the tag itself:

```sh
gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z
```

It rebuilds that tag, publishes its verified assets, then renders, bottles and
publishes the tap. **`--ref` names the tag and is not optional**: the `release`
environment only accepts tags `v*`, so a run started from the default branch
is refused at `publish`. The replay uses the workflow file at that tag, hence
the socle that tag pinned; when the socle is at fault, the remedy is a new
patch release carrying the corrected pin, not a replay.
